# ADR-003: Отказ от хранения учетных данных Active Directory (Zero Password Knowledge)

## Status

Accepted | Implemented (v2.2.2)

## Context

- **Initiator / Decision Owner:** `student1245`
- **Stakeholders:** Пользователи расширения Modeus Student Enhancer (студенты ТюмГУ), разработчики расширения, служба информационной безопасности ТюмГУ.
- **Current state:** Механизм Session Keeper ([ADR-001](ADR-001-silent-session-refresh.md)) успешно продлевает краткосрочные OAuth access-токены (время жизни — 60 минут) через скрытый `iframe` в фоновом режиме, пока действителен сессионный билет поставщика удостоверений ADFS ТюмГУ (`https://fs.utmn.ru/adfs/ls/`). По истечении суточного срока действия билета (24 часа) фоновый рефреш штатно останавливается, и пользователю требуется повторный вход.
- **Why now:** От пользователей регулярно поступает запрос на «вечную сессию без единого ввода пароля» с предложением сохранять логин и пароль от единого корпоративного аккаунта Active Directory (`@utmn.ru`) непосредственно в расширении и автоматически заполнять форму входа ADFS. Необходимо зафиксировать жесткий архитектурный инвариант и нормативный отказ от сбора, хранения и автоматической подстановки паролей, предотвратив фатальные компрометации данных и риски безопасности.
- **Constraints:**
  1. *Same-Origin Policy (SOP) & Browser Sandbox:* Сервер федеративной аутентификации ТюмГУ (`fs.utmn.ru`) и веб-клиент Modeus (`utmn.modeus.org`) принадлежат изолированным Origin. Прямой доступ к DOM формы ввода пароля из контекста Modeus заблокирован платформой Chromium.
  2. *Active Directory Lockout Policy:* Корпоративная политика Active Directory ТюмГУ принудительно блокирует учетную запись студента после 3–5 последовательных неуспешных попыток авторизации.
  3. *Client-Side Execution Boundary:* Клиентское расширение браузера выполняется на недоверенной стороне пользователя и не имеет изолированного аппаратного модуля безопасности (HSM / Secure Enclave).
  4. *Open Source Transparency:* Исходный код расширения полностью открыт на GitHub. Любые механизмы работы с чувствительными данными видны публично и легко поддаются модификации сторонними лицами.
- **Assumptions:**
  - Билет SSO ADFS ТюмГУ выдается со стандартным максимальным сроком жизни 24 часа.
  - Пользователи используют штатные менеджеры паролей современных браузеров (Chrome Password Manager), надежно интегрированные с криптографическими сервисами операционной системы (DPAPI в Windows, Keychain в macOS, Secret Service в Linux).
- **Relevant external factors:**
  - Служба информационной безопасности ТюмГУ ведет постоянный аудит внешних подключений и реагирует на инциденты фишинга учетных записей студентов и сотрудников.

---

## Problem

### Object of Attention
Архитектурная граница ответственности расширения при аутентификации пользователя в корпоративном домене Active Directory ТюмГУ (`fs.utmn.ru`) и преодолении 24-часового барьера истечения SSO-сессии ADFS.

### Current State → Desired State
- *Запрос пользователей (мнимое «желаемое» состояние):* Полное исключение человека из цикла авторизации: расширение запрашивает и сохраняет логин и пароль пользователя, а при истечении 24-часового билета ADFS самостоятельно отправляет учетные данные на сервер, обеспечивая непрерывную «вечную» работу без диалоговых окон.
- *Реальность и конфликт (The Conflict):* Попытка удовлетворить данный запрос превращает легковесный студенческий плагин в кустарный, незащищенный менеджер паролей. Возникает непримиримое противоречие между удобством (Zero-Interaction Login) и критическими угрозами информационной безопасности (утечка учетных записей, блокировка корпоративных сервисов, фишинговые форки и потеря доверия).

### IF / THEN / BUT
- **IF:** Срок действия суточного билета SSO ADFS ТюмГУ истекает по прошествии 24 часов и требует повторного ввода учетных данных студента,
- **THEN:** Сессия должна быть возобновлена с минимальным трением для пользователя,
- **BUT:** Внедрение механизмов перехвата, сохранения и автоматической отправки паролей Active Directory внутри расширения несет критические риски компрометации данных, открывает вектор вредоносных форков в Open Source, угрожает блокировкой учетных записей студентов в Active Directory и разрушает статус доверенного инструмента.

## 1. МОДЕЛЬ УГРОЗ И АНАЛИЗ РИСКОВ (Threat Modeling)

Внедрение любого хранилища паролей в клиентском коде расширения было подвергнуто строгому анализу угроз. Выявлены четыре критические угрозы, делающие хранение учетных данных категорически недопустимым:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        АНАЛИЗ МОДЕЛИ УГРОЗ                             │
├───────────────────────────────────┬────────────────────────────────────┤
│ Угроза 1: Вредоносные OpenSource  │ • Публичный код на GitHub          │
│ форки (Malicious Supply Chain)    │ • Внедрение 2 строк эксфильтрации  │
│                                   │ • Массовый слив паролей в Telegram │
├───────────────────────────────────┼────────────────────────────────────┤
│ Угроза 2: Блокировка в Active     │ • Политика домена: лок через 3-5   │
│ Directory (Brute-force / Lockout) │   неверных попыток ввода           │
│                                   │ • Рассинхрон пароля = паралич ЛК   │
├───────────────────────────────────┼────────────────────────────────────┤
│ Угроза 3: Иллюзия шифрования      │ • Нет HSM / Secure Enclave         │
│ (Client-Side Encryption Fallacy)  │ • Ключ расшифровки доступен в ОЗУ  │
│                                   │ • Бессилие перед локальным malware │
├───────────────────────────────────┼────────────────────────────────────┤
│ Угроза 4: Репутационный крах      │ • Запрос паролей = фишинг          │
│ и классификация как фишинг        │ • Блокировка расширения ИБ ТюмГУ   │
│                                   │ • Тотальная потеря доверия         │
└───────────────────────────────────┴────────────────────────────────────┘
```

### Угроза 1: Вредоносные форки и атаки на цепочку поставок в открытом коде
* **Механика угрозы:** Исходный код расширения открыт на GitHub и распространяется среди студентов в том числе в виде распакованных архивов и форков. Если легитимная кодовая база содержит готовые модули для ввода, хранения и программного сабмита логина и пароля, злоумышленнику достаточно:
  1. Сделать публичный форк репозитория.
  2. Добавить ровно две строчки скрытой эксфильтрации (отправка `login` и `password` через анонимный `fetch` в Telegram-бот или на вебхук).
  3. Собрать zip-архив и распространить его в неофициальных студенческих чатах под видом «улучшенной версии с вечной сессией».
* **Последствия:** Массовая компрометация учетных записей десятков сотен студентов. Поскольку в коде *уже заложена* функциональность работы с паролями, студенты при установке не заподозрят подвоха.
* **Вывод:** Отсутствие самого кода работы с паролями в легитимном проекте является главным барьером безопасности: появление запроса пароля в любой сторонней сборке сразу маркирует её как вредоносную подделку.

### Угроза 2: Блокировка учетной записи в корпоративном Active Directory
* **Механика угрозы:** В Active Directory ТюмГУ действует жесткая корпоративная политика защиты от подбора паролей: при 3–5 последовательных неуспешных попытках аутентификации аккаунт пользователя немедленно и принудительно блокируется администратором домена.
* **Сценарий сбоя:**
  1. Студент меняет пароль от личного кабинета через официальный портал университета или забывает об истечении срока действия пароля.
  2. Локальное хранилище расширения продолжает содержать старый кэшированный пароль.
  3. Фоновый механизм Session Keeper или скрипт автологина предпринимает несколько автоматических попыток входа подряд с невалидными данными.
* **Последствия:** Мгновенная блокировка доменной учетной записи студента. Студент лишается доступа не только к Modeus, но и к корпоративной почте Microsoft Outlook/Exchange, порталу государственных сервисов, закрытым ресурсам библиотеки, университетскому Wi-Fi и личному кабинету обучающегося прямо посреди сессии или записи на дисциплины.

### Угроза 3: Иллюзия безопасности клиентского шифрования (Client-Side Encryption Fallacy)
* **Механика угрозы:** Попытки «защитить» пароли в расширении с помощью WebCrypto API (например, алгоритмом `AES-GCM-256`) создают опасную иллюзию безопасности:
  1. В расширении браузера отсутствует аппаратный модуль безопасности (Hardware Security Module, HSM / TPM / Secure Enclave).
  2. Требование пользователей состоит в «бесшовности без ввода мастер-пароля», что означает необходимость автоматической генерации или извлечения ключа расшифрования самим скриптом.
  3. Любой симметричный ключ, сформированный на основе статических параметров (UUID пользователя, константы скрипта, `chrome.runtime.id`), тривиально извлекается любым скриптом или утилитой анализа памяти.
* **Последствия:** Шифрование без мастер-пароля защищает исключительно от беглого просмотра файла глазами в DevTools, но абсолютно бесполезно против:
  - любого вредоносного ПО (инфостилеров, инжекторов), действующего на компьютере пользователя;
  - других установленных расширений с расширенными правами доступа;
  - прямого анализа локального хранилища браузера (`chrome.storage.local` / `IndexedDB`).

### Угроза 4: Удар по репутации, подозрение в фишинге и конфликт со службой безопасности
* **Механика угрозы:** Расширение декларирует в манифесте сетевые привилегии к доменам `https://utmn.modeus.org/*` и `https://fs.utmn.ru/*`.
* **Последствия:** Если стороннее неофициальное расширение начнет отрисовывать собственные поля ввода пароля или перехватывать ввод на странице `fs.utmn.ru`:
  1. Пользователи обоснованно классифицируют такое поведение как фишинг и попытку кражи корпоративных данных.
  2. Служба информационной безопасности университета немедленно инициирует расследование, внесет расширение в черный список и заблокирует аккаунты разработчиков и пользователей.
  3. Проект потеряет академическое доверие и официальное признание студенческим сообществом.

## 2. ПРИЧИНЫ ОТКАЗА ОТ АЛЬТЕРНАТИВ

В процессе проектирования архитектуры Session Keeper были детально исследованы и отвергнуты четыре альтернативных подхода преодоления 24-часового барьера:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        ОТКЛОНЕННЫЕ АЛЬТЕРНАТИВЫ                        │
├───────────────────────────────┬────────────────────────────────────────┤
│ Альтернатива 1:               │ ❌ Сброс состояния Angular SPA, потеря │
│ Полный редирект вкладки       │    несохраненных форм, таймеров и      │
│                               │    фокуса ввода                        │
├───────────────────────────────┼────────────────────────────────────────┤
│ Альтернатива 2:               │ ❌ Блокировка CORS сервером ADFS,      │
│ Фоновый сетевой fetch()       │    безвозвратная потеря хэша с токеном │
│                               │    (#access_token) при 302-редиректе   │
├───────────────────────────────┼────────────────────────────────────────┤
│ Альтернатива 3:               │ ❌ Нарушение Same-Origin Policy (SOP): │
│ Скрытый iframe с автологином  │    родительское окно utmn.modeus.org   │
│                               │    не имеет доступа к DOM fs.utmn.ru   │
├───────────────────────────────┼────────────────────────────────────────┤
│ Альтернатива 4:               │ ❌ Категорически отвергнуто по модели  │
│ Кустарное хранилище паролей   │    угроз (Supply chain, AD lockout,    │
│ (Custom Password Vault)       │    инфостилеры, фишинг)                │
└───────────────────────────────┴────────────────────────────────────────┘
```

### Альтернатива 1: Полный редирект вкладки (`window.location.href`)
- **Суть:** При истечении 24-часового билета принудительно направлять основную вкладку браузера на URL авторизации `https://auth.modeus.org/oauth2/authorize` с последующим проходом через ADFS.
- **Причина отказа:** Катастрофическая деградация пользовательского опыта. Полная перезагрузка страницы уничтожает состояние Angular SPA, сбрасывает введенные данные фильтров, прерывает интерактивную запись на элективы по физкультуре и сбивает позицию скролла в расписании.

### Альтернатива 2: Фоновый сетевой запрос (`fetch` / `XMLHttpRequest`)
- **Суть:** Попытка программно эмулировать процесс входа через отправку учетных данных фоновым POST-запросом к `https://fs.utmn.ru/adfs/ls/`.
- **Причина отказа:**
  1. *CORS Restriction:* Сервер ADFS ТюмГУ не отдает разрешающие заголовки `Access-Control-Allow-Origin: https://utmn.modeus.org`, в связи с чем браузер блокирует ответ на сетевом уровне.
  2. *Fragment Loss:* Согласно стандартам W3C Fetch API и HTML Living Standard, при цепочке HTTP 302-редиректов фрагмент URI (`#access_token=...`), несущий токены авторизации OAuth Implicit Flow, физически отбрасывается браузером и не возвращается скрипту.
  3. Невозможность обработки многофакторной аутентификации, капчи и защиты от CSRF формы ADFS вслепую.

### Альтернатива 3: Скрытый iframe с автоматическим заполнением формы (Auto-Submit)
- **Суть:** Загрузка страницы логина ADFS внутри скрытого элемента `<iframe>` с последующим поиском элементов `<input id="userNameInput">` и `<input id="passwordInput">` и отправкой формы.
- **Причина отказа:**
  1. *Same-Origin Policy (SOP):* Домен `https://fs.utmn.ru` и домен `https://utmn.modeus.org` изолированы браузером. Родительский документ не имеет права читать или модифицировать DOM-дерево дочернего фрейма другого происхождения (`SecurityError: Blocked a frame with origin from accessing a cross-origin frame`).
  2. Внедрение скриптов расширения непосредственно в контекст `fs.utmn.ru` для обхода SOP создало бы полноценный кейлоггер внутри домена авторизации, что нарушает правила безопасности Chrome Web Store и классифицируется антивирусным ПО как вредоносная активность.

### Альтернатива 4: Внедрение кустарного хранилища паролей (Custom Password Vault)
- **Суть:** Создание собственного хранилища логина и пароля в `chrome.storage.local` с шифрованием на WebCrypto.
- **Причина отказа:** Категорически отклонено по результатам комплексного моделирования угроз (см. Раздел 1). Не решает проблему аппаратной безопасности, создает вектор вредоносных форков и влечет риск блокировки корпоративных учетных записей студентов в Active Directory.

## 3. ПРИНЯТОЕ РЕШЕНИЕ (Архитектурный инвариант)

Мы фиксируем фундаментальный архитектурный инвариант проекта Modeus Student Enhancer:

> **ПОЛНЫЙ И БЕЗОГОВОРОЧНЫЙ ОТКАЗ ОТ СБОРА, ХРАНЕНИЯ, ОБРАБОТКИ И АВТОМАТИЧЕСКОЙ ПОДСТАНОВКИ ПАРОЛЕЙ УЧЕТНЫХ ЗАПИСЕЙ ACTIVE DIRECTORY ТЮМГУ (СТАТУС ZERO PASSWORD KNOWLEDGE).**

```text
┌────────────────────────────────────────────────────────────────────────┐
│             АРХИТЕКТУРНЫЙ ИНВАРИАНТ: ZERO PASSWORD KNOWLEDGE           │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   [ Вкладка Modeus: Angular SPA ]                                      │
│                 │                                                      │
│                 │  Каждые 60 минут: фоновое продление                  │
│                 ▼                                                      │
│     [ Session Keeper: скрытый iframe ] (ADR-001)                       │
│     Продление токена работает, пока жив 24-часовой ADFS SSO билет      │
│                 │                                                      │
│                 │  Истечение 24 часов (ADFS тикет протух)              │
│                 ▼                                                      │
│     [ ДЕЛЕГИРОВАНИЕ БРАУЗЕРУ И ОПЕРАЦИОННОЙ СИСТЕМЕ ]                  │
│     • Остановка Session Keeper (Circuit Breaker)                       │
│     • Переход на официальную форму https://fs.utmn.ru                  │
│     • Работа встроенного Chrome Password Manager (DPAPI / Keychain)    │
│     • Нулевое участие кода расширения в обработке паролей              │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

### Ключевые положения решения:

1. **Принцип наименьших привилегий (Principle of Least Privilege):**
   - Расширение оперирует исключительно временными сессионными токенами (`access_token`, `id_token`), полученными легитимным путем через стандартный протокол OAuth 2.0.
   - Расширение обладает статусом **Zero Password Knowledge**: в кодовой базе физически отсутствуют переменные, поля ввода, функции шифрования или структуры данных, предназначенные для хранения пользовательских паролей.

2. **Граница сессии — 24-часовой срок билета ADFS:**
   - Фоновое бесшовное продление сессии через Session Keeper ([ADR-001](ADR-001-silent-session-refresh.md)) действует строго в пределах жизненного цикла тикета поставщика удостоверений ТюмГУ (24 часа).
   - В течение учебного дня (до 24 часов) студент работает полностью бесшовно без единого выброса на экран логина.

3. **Делегирование аутентификации браузеру и операционной системе:**
   - По истечении 24 часов сессионный билет ADFS естественным образом аннулируется сервером.
   - Срабатывает предохранитель Circuit Breaker: расширение останавливает попытки рефреша, информирует пользователя понятным уведомлением и передает управление штатному механизму браузера.
   - Пользователь переходит на официальную страницу `https://fs.utmn.ru`, где аутентификация выполняется доверенным, аппаратно-защищенным способом:
     - встроенный менеджер паролей Chromium (**Chrome Password Manager**);
     - криптографическая изоляция ключей средствами ОС (**Windows DPAPI**, **macOS Keychain**, **Linux Secret Service**);
     - поддержка биометрии (Windows Hello, Touch ID) и корпоративных двухфакторных политик (MFA).

### Why
Данный подход обеспечивает идеальный баланс между практическим удобством студентов (непрерывная работа до 24 часов без единого логина) и бескомпромиссной безопасностью корпоративной инфраструктуры, исключая риски компрометации данных, вредоносных форков и блокировки аккаунтов.

### Trade-offs
- Мы принимаем необходимость для пользователя **один раз в 24 часа** подтвердить вход на официальной странице `fs.utmn.ru` в обмен на:
  - 100% гарантию сохранности корпоративных учетных записей студентов;
  - полное исключение риска блокировки аккаунта в Active Directory;
  - безупречную репутацию и прозрачность открытого исходного кода расширения.

---

## Non-Goals

- Создание встроенного в расширение хранилища паролей или менеджера учетных записей.
- Преодоление 24-часового лимита безопасности Active Directory ADFS без участия пользователя.
- Внедрение пользовательских настроек вида «Сохранять мой пароль для автологина (небезопасно)».
- Перехват или анализ содержимого полей ввода на домене `fs.utmn.ru`.
- Попытки программного подбора или валидации учетных данных студента.

## Consequences

### Positive
- **Абсолютная безопасность учетных данных:** Расширение невозможно скомпрометировать ради кражи паролей студентов, так как пароли в нем никогда не хранятся.
- **Защита от вредоносных форков:** Любая модификация расширения, запрашивающая пароль, сразу распознается студенческим сообществом как вредоносный фишинг.
- **Нулевой риск блокировки в Active Directory:** Исключены инциденты блокировки корпоративной почты и личного кабинета из-за рассинхронизации паролей.
- **Доверие со стороны университета:** Соответствие требованиям информационной безопасности и прозрачность Open Source проекта.
- **Использование лучших практик безопасности ОС:** Пароли защищены на аппаратном уровне (DPAPI/TPM/Keychain), а не хрупкими скриптами расширения.

### Negative / Trade-offs
- Раз в 24 часа пользователю требуется сделать один клик для подтверждения входа через официальную страницу ADFS (при сохраненном пароле в Chrome — ровно одно нажатие кнопки «Войти»).

## Implementation Contract

### Scope
Политика безопасности и правила обращения с учетными данными пользователей во всех модулях расширения (`keeper-early.js`, `content.js`, `injected.js`, `pe-module.js`, `popup.js`).

### Affected Areas
- `manifest.json` — запрет на добавление привилегий для скрытого перехвата форм ввода.
- `injected.js` — блок Session Keeper (строгий лимит попыток Circuit Breaker, отсутствие парольной логики).
- `popup.html` / `popup.js` — запрет на создание элементов UI для ввода учетных данных.
- `README.md` / документация — фиксация политики безопасности для пользователей и контрибьюторов.

### Required Changes & Behavior
1. Session Keeper обязан прекращать попытки фонового рефреша при срабатывании Circuit Breaker (`SESSION_MAX_REFRESH_ATTEMPTS = 5`) и отображать toast-уведомление о необходимости повторного входа.
2. При логауте или протухании сессии бэкап `localStorage.mse_auth_backup` обязан полностью удаляться.
3. Любое перенаправление на страницу входа должно вести исключительно на официальный URL аутентификации `https://utmn.modeus.org/` или `https://auth.modeus.org/oauth2/authorize`.

### Patterns to Follow
- Делегирование авторизации доверенному системному агенту (браузер + Chrome Password Manager).
- Принцип наименьших привилегий (Zero Password Knowledge).
- Прозрачность сетевой активности и четкое логирование статусов сессии с таймштампами (`[MSE Session]`).

### Patterns to Avoid (СТРОЖАЙШИЙ ЗАПРЕТ)
- ❌ **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** добавлять поля ввода пароля в интерфейс расширения (`popup.html`, модальные окна, настройки).
- ❌ **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** сохранять пароли в любых браузерных хранилищах (`localStorage`, `sessionStorage`, `chrome.storage`).
- ❌ **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** внедрять content script на страницу `https://fs.utmn.ru/*` с целью чтения или манипуляции элементами формы авторизации.
- ❌ **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать любые схемы клиентского шифрования (WebCrypto AES-GCM) для паролей без мастер-пароля.

### Dependencies & Configuration
- Нативные механизмы браузера: Chromium Password Manager, Web Crypto API (только для генерации случайных nonce/state, но не для паролей).
- Зависимости: 0 внешних библиотек.

### Data Migration & Rollback
- Никакой миграции данных не требуется, так как учетные данные никогда не сохранялись и не будут сохраняться.
